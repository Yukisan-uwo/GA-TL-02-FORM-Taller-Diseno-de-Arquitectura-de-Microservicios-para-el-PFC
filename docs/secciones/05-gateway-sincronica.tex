\section{API Gateway y comunicación síncrona}
\subsection{Diseño del API Gateway}

El API Gateway será el punto de entrada del cliente web del SGRA.
Recibirá las solicitudes por HTTPS y las enviará al microservicio
correspondiente según la ruta y el método HTTP. Por ejemplo, una
solicitud de refuerzo se dirige al servicio Refuerzos, mientras que
una consulta de aulas disponibles se dirige al servicio Espacios.

Para el diagrama C4 se proponen tres componentes del Gateway:
el enrutador, el filtro de acceso y el filtro de control de tráfico.
El enrutador dirige cada solicitud. El filtro de acceso valida el
token en las rutas protegidas. El filtro de tráfico limita la
cantidad de solicitudes que recibe el Gateway. Cada microservicio
comprueba si el usuario tiene permiso sobre el recurso solicitado.

Al modificar una solicitud, Refuerzos verifica el rol, el acceso
al recurso y el estado actual. El estudiante puede cancelar su
solicitud mientras esté pendiente. El docente puede registrar
si la acepta o la rechaza. El cierre de una sesión académica
registra sus resultados en Refuerzos. El cierre de la sesión de
usuario corresponde a Identidad y acceso.

La configuración de correo del RF13.5 se realiza por la ruta de
administración de Notificaciones. El envío de avisos del RF14
se activa mediante eventos, según la comunicación asíncrona.

\subsection{Llamadas síncronas entre microservicios}

\textbf{De Refuerzos a Académico.}
Antes de guardar una solicitud, Refuerzos llama a
\texttt{GET} \path|/interno/matriculas/vigentes| para comprobar la
matrícula del estudiante en la asignatura y el período correspondientes.

\textbf{De Refuerzos a Espacios.}
Al programar o reprogramar una sesión presencial, Refuerzos solicita
la reserva mediante \texttt{PUT} \path|/interno/reservas/{idSesion}|.
Espacios comprueba la disponibilidad y devuelve el estado de la
reserva, que puede quedar pendiente de gestión. Si se agota el tiempo
de espera, Refuerzos conserva el estado pendiente y consulta
\texttt{GET} \path|/interno/reservas/{idSesion}| antes de reenviar la
petición. Refuerzos confirma el espacio de la sesión cuando Espacios
confirma la reserva.

Las rutas \path|/interno/| se usan entre servicios. El gestor de
espacios opera desde el cliente web mediante las rutas públicas de
reservas que atiende el Gateway.

\subsection{Selección de REST y relación con los RNF}

Se propone REST sobre HTTPS con JSON para las solicitudes del cliente
web y las llamadas síncronas entre microservicios. Angular puede
consumir respuestas JSON con su cliente HTTP para consultar o modificar
recursos como solicitudes, sesiones y reservas \cite{sgra-angular-http}.

gRPC también admite intercambios de petición y respuesta mediante
contratos definidos con Protocol Buffers. Para usarlo desde el
navegador habría que integrar gRPC-Web \cite{sgra-grpc-web}. El diseño
adopta REST en ambos canales para usar el mismo esquema de métodos
HTTP y mensajes JSON en el cliente y en las integraciones internas.
Las metas de rendimiento y disponibilidad se comprobarán con pruebas
del sistema.

\begin{itemize}
    \item \textbf{RNF01, rendimiento.} El tiempo máximo de respuesta
    es de 5 segundos con hasta 100 usuarios concurrentes y
    10\,000 solicitudes registradas. El Gateway y los clientes
    internos tendrán tiempos de espera acotados dentro del límite
    de la petición. La meta se probará de extremo a extremo con Azure
    como entorno de referencia provisional.

    \item \textbf{RNF02, disponibilidad.} La disponibilidad mensual
    mínima es de 99{,}5\,\%, excluyendo los mantenimientos programados
    notificados con 24 horas de anticipación. Se proponen réplicas del
    Gateway detrás de un balanceador con comprobaciones de salud.
    El Gateway podrá responder HTTP~503 ante indisponibilidad temporal
    o HTTP~504 si se agota el tiempo de espera del servicio consultado
    \cite{sgra-http-semantics}.

    \item \textbf{RNF03, usabilidad.} La interfaz mostrará estados y
    errores comprensibles en las operaciones principales. Se evaluará
    si los usuarios de cada rol completan sus tareas sin ayuda externa
    y si el promedio de la escala SUS llega a 70 puntos.

    \item \textbf{RNF04, compatibilidad.} Se comprobará el
    funcionamiento en las dos últimas versiones estables de Chrome,
    Firefox, Edge y Safari, sin complementos adicionales.

    \item \textbf{RNF05, auditoría.} Los servicios registrarán el
    100\,\% de las operaciones críticas con usuario, fecha y hora.
    Administración conservará ese historial en un registro de solo
    anexado. Los perfiles administrativos podrán consultar los
    registros y generar reportes de auditoría.

    \item \textbf{RNF06, integridad.} Cada servicio comprobará el
    permiso sobre el recurso antes de cualquier modificación. Las
    pruebas comprobarán el rechazo de modificaciones no autorizadas
    y la correspondencia entre los datos almacenados y los reportes
    generados, comparados en el mismo punto de corte.
\end{itemize}
