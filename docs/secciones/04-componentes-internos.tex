\section{Componentes internos}

El diagrama C4 de nivel 3 muestra las piezas internas de cada
microservicio y la forma en que se relacionan. Para mantener un
diseño uniforme, todos los servicios siguen una organización en
capas: un componente de entrada que recibe las solicitudes, un
componente de lógica que aplica las reglas del dominio y un
componente de acceso a datos que es el único autorizado para
consultar la base propia del servicio. Cuando un servicio necesita
información de otro dominio, utiliza un cliente REST o un
componente de mensajería, nunca la base de datos ajena
\cite{microsoft-data-sovereignty}.

\subsection{Relaciones y dependencias}

Las dependencias síncronas se limitan a las dos llamadas descritas
en la sección del API Gateway: Refuerzos consulta a Académico para
validar la matrícula y solicita a Espacios la reserva de las
sesiones presenciales. Ambas se realizan desde clientes REST
internos con tiempo límite, de modo que una demora en Académico o
Espacios no bloquea indefinidamente al servicio de Refuerzos.

Notificaciones y Seguimiento no son invocados directamente por
otros servicios. Ambos dependen únicamente de los eventos que
publican Refuerzos y Espacios, por lo que una caída temporal de
cualquiera de ellos no impide registrar solicitudes ni programar
sesiones; los eventos pendientes se procesan cuando el servicio
se recupera. Identidad y acceso es utilizado por el filtro de acceso
del Gateway, mientras que Administración recibe los registros de
auditoría de los demás servicios.

Esta organización reduce el acoplamiento entre dominios: los
servicios centrales del proceso de refuerzo conservan su
funcionamiento aunque fallen los servicios de apoyo, lo que
contribuye a la disponibilidad planteada en el RNF02.
